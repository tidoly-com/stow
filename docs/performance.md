# 메모리 · 속도 — 잰 것과 안 잰 것

tidoly stow 가 얼마나 가벼운지에 대해 지금까지 잰 숫자를 모았다. **8GB 노트북에서 사진 1만 5천 장(53GB)을 처리하는 동안 프로그램 전체가 가장 많이 쓴 메모리는 1.7GB 였고, 장비의 여유 메모리는 4.4GB 아래로 내려가지 않았다**(아래 첫 절). 나머지 숫자는 메모리가 넉넉한 장비(Apple M5 Pro · 64GB, 일부는 Windows 11 x64)에서 쟀다. 2GB · 4GB 장비에서는 아직 재지 않았다.

## 8GB 노트북에서 사진 1만 5천 장 (2026-10-18)

오래된 노트북에 리눅스로 설치하고, 아이폰을 PC 로 옮겨 둔 사진 폴더를 "기존 사진 폴더" 로 등록해 끝날 때까지 쟀다.

- 장비: Intel i7-8550U(4코어 8스레드) · 메모리 7GB · 7200RPM 하드디스크 하나(ext4) · 유선
- 사진: 14,882 파일 · 53GB — HEIC 5,555 · MOV 3,996 · JPG 3,759 · PNG 909 · AAE 584 · MP4 31. 라이브 포토를 묶고 나면 사진 · 영상 10,717개
- 작업자 4(코어 수의 절반), 얼굴인식 · 화면 캡처 켬, 쿠폰인식 켬. 처리하는 동안 사진 화면을 열어 두었다

| 무엇 | 잰 값 |
|---|---|
| 프로그램 전체 메모리 최고 | **1,678MB** (서버 · 얼굴 도우미 · ffmpeg 합) |
| 얼굴 도우미 최고 | **1,349MB** — 원본(긴 변 2880)까지 보는 설정. 맥에서 잰 1,370MB 와 같다 |
| 서버 | 보통 150MB 안팎, 최고 817MB |
| ffmpeg (HEIC · 동영상 작은 그림) | 한꺼번에 돈 것의 합 최고 531MB |
| 장비 여유 메모리 최저 | **4,400MB** (7GB 중) |
| 다 끝난 뒤 | 프로그램 92MB. 얼굴 도우미는 일이 없어 내려간다 |
| 정보 읽기가 끝나기까지 | 2시간 22분 |
| 작은 그림이 거의 다 되기까지 | 2시간 45분 — 파일 28,524개 · 3.9GB |
| 얼굴 · 장소 · 쿠폰까지 모두 끝나기까지 | **약 4시간** |
| DB | 22MB |

- **깨끗한 조건의 시간은 아니다.** 처리 중에 고친 빌드로 서버를 여러 번 다시 켰고(이어서 처리한다), 중간 한 시간은 같은 하드디스크로 큰 복사가 겹쳐 데이터베이스 쓰기가 밀렸다 — 이때 "database is locked" 가 났고, 끝난 작업 일부가 "하는 중" 으로 남았다. 둘 다 다음 버전에서 고쳤다(CHANGELOG).
- **부하:** ffmpeg 가 스레드 제한 없이 돌 때 1분 평균 부하는 보통 25–33, 한 번 135 까지 올랐고 사진 화면이 7.6초 걸렸다. ffmpeg 를 하나에 CPU 1개 · 낮은 우선순위로 바꾼 뒤에도 부하는 보통 25–43(최고 64)으로 비슷했지만, 사진 화면은 0.15–0.25초가 됐고 처리도 느려지지 않았다 — 앞뒤 한 시간씩 견주면 정보 읽기가 분당 약 91 → 129장, 작은 그림 파일이 분당 약 176 → 253개(다시 켠 시간이 앞쪽에 끼어 있어 깨끗한 비교는 아니다). 작은 그림이 끝난 뒤(얼굴 · 장소만 남았을 때)는 6 안팎이다.
- 처리 순서는 정하지 않았다 — 들어온 순서대로다. 작은 그림 · 정보 읽기가 먼저 끝나고 얼굴은 그 뒤에 몰려 끝났다.

## 사진 서버 본체 (`tidoly-light`)

| 무엇 | 잰 값 | 조건 |
|---|---|---|
| 1GB 파일 하나를 받는 동안 | 받기 전 **21MB**, 받는 동안 최고 **21MB** — 파일 크기만큼 늘지 않는다 | 로컬, 1.69초 |
| 사진 1,000장 올리고 정보 읽기 · 작은 그림 만들기까지 | 메모리 최고 **210MB**(시작 135MB), 올리기 4초, 모두 끝나기까지 **38초**, 작은 그림 94MB | 작업자 2. 시험 그림은 단순한 무늬라 진짜 사진보다 빨리 풀린다 |

- 1억 2천만 화소가 넘는 JPEG 는 메모리 때문에 풀지 않는다(갤럭시의 2억 화소 모드가 여기에 걸린다).

## 얼굴 도우미 (`stow-faces`, Go + ONNX Runtime)

사진이 들어오는 동안만 뜨고, 일이 없으면 3분 뒤 내려간다. 메모리를 가장 많이 쓰는 부분이다. 자세한 것은 `docs/barcodes-and-faces.md`.

| 무엇 | 최대 메모리 | 한 장에 |
|---|---|---|
| 미리보기(긴 변 1440)만 볼 때 — 맥 | **352MB** | 35ms |
| 미리보기만 볼 때 — 윈도 | **220MB** | |
| 원본(긴 변 2880)까지 볼 때 — 맥 | **1,370MB** | 85ms |

- 맥에서는 ONNX Runtime 의 KleidiAI 를 꺼야 이 값이 나온다(켜면 640–880MB).
- 원본까지 보면 얼굴을 열에 하나쯤 더 찾는 대신 메모리가 네 배가 된다.

| 무엇 | 잰 값 |
|---|---|
| 사진 10만 장 + 장마다 512개 숫자(벡터) | 2.09초에 기록, 파일 397MB |
| 쓰기 4 · 타임라인 읽기 8 동시에 | 쓰기 초당 약 3만, 실패 0, 읽기 p50 2.2ms · p99 4.6ms |
| 벡터 10만 개 훑기 검색(색인 없음) | 메모리 202MB, 한 번에 34ms |

## 견주어 본 것 — Immich 서버 묶음

2026-10-12 시험에서 Immich 서버(Docker 묶음)를 Nextcloud · Paperless 와 함께 띄웠을 때, **가만히 있는 상태에서 사진(Immich) 부분이 약 1.67GB** 였다. 사진을 처리하는 동안이나 Immich 의 머신러닝 부분이 일할 때는 재지 않았다. 같은 조건에서 tidoly stow 와 나란히 잰 것이 아니므로, 둘을 숫자 하나로 비교하지 않는다.

## 아직 안 잰 것

- **2GB · 4GB 장비**에서의 최대 메모리 — 얼굴 인식을 켜고 / 끄고, 원본까지 보기를 끄고
- 같은 1만 5천 장을 다시 켜기 · 큰 복사 없이 처음부터 끝까지 한 번에 처리하는 시간
- 폰 앱으로 올리는 동안(폴더 등록이 아니라)의 메모리와 시간
- 맥 쿠폰 도우미(Vision)의 메모리
- 느린 디스크(USB 하드, SD 카드)에서의 속도

메모리를 제한한 VM(예: 2GB)이나 작은 장비에 설치해, 사진 수천 장을 넣으면서 서버와 얼굴 도우미의 최대 메모리를 재면 위의 첫 줄이 채워진다.
